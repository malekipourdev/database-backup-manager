@@article overview /overview
@title معرفی DevOps Manager
@summary پنل چه کارهایی انجام می‌دهد و هر بخش منو برای چیست.
DevOps Manager از پایگاه‌های داده‌ی **MySQL** و **MariaDB** پشتیبان (بکاپ) می‌گیرد و آن‌ها را بررسی و نگهداری می‌کند، برنامه‌های شما را از git استقرار (دیپلوی) می‌دهد و کانتینرهای Docker را روی یک یا چند سرور زیر نظر دارد و کنترل می‌کند. همه‌چیز روی سرور خودتان اجرا می‌شود و داده‌ای به جای دیگری فرستاده نمی‌شود، مگر خودتان بخواهید (مثلاً فضای ابری یا ربات).

## سرور فعال

پنل می‌تواند چند سرور را مدیریت کند. پایین منوی کناری (در موبایل، دکمه‌ی نام سرور بالای صفحه) کارت **«سرور فعال»** هست: هر سروری که آن‌جا انتخاب شود، بخش‌های نمای کلی، پایگاه‌های داده، تاریخچه‌ی بکاپ‌ها، زمان‌بندی‌ها، پروژه‌ها و کانتینرها **فقط مال همان سرور** را نشان می‌دهند. بقیه‌ی بخش‌ها برای همه‌ی سرورها مشترک‌اند. ([راهنمای سرور فعال](#current-server))

## بخش‌های منو

منو از بزرگ به کوچک گروه‌بندی شده است: سرور، بعد برنامه‌ها، بعد پایگاه‌های داده. گروه‌ها جمع می‌شوند: با زدن روی نام گروه بازش کنید یا ببندید؛ گروه صفحه‌ای که در آن هستید خودش باز می‌شود.

| گروه                        | بخش                   | کاربرد                                                                         |
| --------------------------- | --------------------- | ------------------------------------------------------------------------------ |
|                             | نمای کلی              | (سرور فعال) سلامت سرور، بکاپ‌های ۲۴ ساعت گذشته، کانتینرها، استقرارها و مشکلات  |
| مدیریت سرور                 | وب‌سرورها             | (سرور فعال) nginx و Apache: سایت‌ها، گواهی‌ها و پایش سلامت                     |
| برنامه‌ها                   | پروژه‌ها              | (سرور فعال) استقرار برنامه‌ها از git با docker compose                         |
|                             | کانتینرها             | (سرور فعال) دیدن و کنترل کانتینرهای Docker                                     |
| پایگاه داده و پشتیبان‌گیری  | پایگاه‌های داده       | (سرور فعال) افزودن MySQL/MariaDB، آزمایش اتصال، انتخاب دیتابیس‌ها و گرفتن بکاپ |
|                             | تاریخچه‌ی بکاپ‌ها     | (سرور فعال) دانلود، حذف و بارگذاری دوباره                                      |
|                             | زمان‌بندی‌ها          | (سرور فعال) بکاپ خودکار در زمان‌های مشخص                                       |
|                             | ذخیره‌سازی و نگهداری  | تنظیمات بکاپ، فضای ابری (S3) و سیاست نگهداری                                   |
| هشدار و دسترسی از پیام‌رسان | هشدارها               | هشدار خطاها و رویدادها در بله، تلگرام و وب‌هوک                                 |
|                             | ربات‌های بله و تلگرام | مدیریت از داخل بله و تلگرام                                                    |
| سیستم                       | امنیت حساب            | ورود دو مرحله‌ای و کدهای بازیابی                                               |
|                             | راهنما                | همین راهنما                                                                    |

خود سرورها در **«مدیریت همه‌ی سرورها»** داخل کارت سرور فعال اضافه، متصل و بررسی می‌شوند.

**رفتن به…** (بالای منوی کناری، یا `Ctrl+K` یا `/`) با تایپ چند حرف هر صفحه را پیدا می‌کند یا سرور را عوض می‌کند.

## از کجا شروع کنم؟

اگر تازه پنل را نصب کرده‌اید، [گام‌های اول](#first-steps) را دنبال کنید.

@@article install
@title نصب و راه‌اندازی
@summary نصب پنل روی سرور لینوکسی با Docker در چند دستور.
پیش‌نیاز: یک سرور لینوکس با **Docker** و **Compose v2** و ابزار `openssl`.

## ۱. گرفتن کد

```bash
git clone https://github.com/malekipourdev/database-backup-manager.git mysql-backup-panel
cd mysql-backup-panel
```

اگر مخزن خصوصی است، با deploy key یا توکن شخصی clone کنید یا پوشه را با `scp` منتقل کنید.

## ۲. ساخت فایل `.env`

```bash
KEY=$(openssl rand -base64 32 | tr '+/' '-_')
PASS=$(openssl rand -base64 18 | tr -d '/+=')
cat > .env <<EOF
MBP_ENCRYPTION_KEY=$KEY
MBP_ADMIN_USERNAME=admin
MBP_ADMIN_PASSWORD=$PASS
MBP_BIND_ADDRESS=127.0.0.1
MBP_HTTP_PORT=8080
MBP_COOKIE_SECURE=true
EOF
chmod 600 .env
echo "Admin password: $PASS"
```

> ! از `MBP_ENCRYPTION_KEY` حتماً یک نسخه جای امن (مثلاً password manager) نگه دارید. همه‌ی رمزهای ذخیره‌شده با این کلید رمزنگاری می‌شوند و بدون آن قابل بازیابی نیستند.

## ۳. اجرا

```bash
docker compose up -d --build
ss -tlnp | grep 8080
```

خروجی دستور دوم باید `127.0.0.1:8080` باشد، نه `0.0.0.0:8080`.

سپس با [تونل SSH](#access) پنل را باز کنید و با نام کاربری `admin` و رمز چاپ‌شده وارد شوید. بعد از اولین ورود می‌توانید خط `MBP_ADMIN_PASSWORD` را از `.env` پاک کنید؛ فقط برای ساخت اولین مدیر استفاده می‌شود.

@@article access
@title دسترسی امن با تونل SSH
@summary چرا پنل فقط روی 127.0.0.1 باز است و چطور از کامپیوتر خودتان به آن وصل شوید.
پنل به‌صورت پیش‌فرض فقط روی `127.0.0.1:8080` خود سرور در دسترس است؛ یعنی از اینترنت دیده نمی‌شود و نیازی به دامنه، گواهی TLS یا باز کردن پورت ندارید.

روی کامپیوتر خودتان این دستور را اجرا کنید و تا وقتی با پنل کار دارید باز بماند:

```bash
ssh -N -L 8080:127.0.0.1:8080 user@SERVER_IP
```

سپس در مرورگر `http://localhost:8080` را باز کنید. اگر پورت 8080 روی کامپیوترتان اشغال است، مثلاً از `-L 18080:127.0.0.1:8080` و نشانی `http://localhost:18080` استفاده کنید.

> چرا فقط با فایروال پورت را نبندیم؟ Docker قوانین iptables خودش را می‌نویسد و از ufw عبور می‌کند؛ پورتی که روی `0.0.0.0` منتشر شود حتی با ufw هم باز است. پس `MBP_BIND_ADDRESS=127.0.0.1` را نگه دارید، مگر پشت یک reverse proxy با TLS یا شبکه‌ی خصوصی امن باشید.

@@article first-steps
@title گام‌های اول پس از ورود
@summary چک‌لیست راه‌اندازی کامل: از اولین بکاپ تا هشدارها.

1. **حساب را امن کنید:** در [حساب کاربری](/account) ورود دو مرحله‌ای را روشن کنید ([راهنما](#two-factor)).
2. **پایگاه داده اضافه کنید:** در [پایگاه‌های داده](/instances/new) نشانی و کاربر دیتابیس را وارد و «آزمایش اتصال» را بزنید ([راهنما](#add-database)).
3. **دیتابیس‌ها را علامت بزنید:** در صفحه‌ی همان پایگاه داده، دیتابیس‌هایی را که باید بکاپ بگیرند انتخاب و ذخیره کنید.
4. **یک بکاپ دستی بگیرید** و در [پشتیبان‌ها](/backups) نتیجه را ببینید.
5. **زمان‌بندی بسازید** تا بکاپ خودکار شود ([راهنما](#schedules)).
6. **فضای ابری را وصل کنید** تا نسخه‌ای بیرون از سرور هم داشته باشید ([راهنما](#remote-storage)).
7. **سیاست نگهداری** تعیین کنید تا دیسک پر نشود ([راهنما](#retention)).
8. **اعلان‌ها و ربات** را راه بیندازید تا از خطاها باخبر شوید ([راهنما](#notifications)).
9. از خود پنل هم [پشتیبان](#panel-backup) داشته باشید.

@title زبان، ظاهر و موبایل
@summary تغییر زبان، کار با پنل روی گوشی و جستجو در راهنما.

- **رفتن به…:** هر جا Ctrl+K (یا /) را بزنید، بخشی از نام صفحه یا سرور را تایپ کنید و Enter بزنید.
- **صفحه‌کلید:** اولین Tab به «رفتن به محتوای اصلی» می‌رسد؛ بعد از باز شدن هر صفحه، فوکوس روی عنوان آن است.
- **زبان:** از دکمه‌ی «فارسی / English» بالای صفحه. انتخاب شما در همین مرورگر ذخیره می‌شود. زبان ربات برای هر مدیر جداگانه از داخل خود ربات انتخاب می‌شود.
- **موبایل:** روی صفحه‌های کوچک، نوار پایین صفحه نمای کلی، کانتینرها، پروژه‌ها و پایگاه‌های داده را دارد؛ دکمه‌ی **منو** بقیه‌ی صفحه‌ها، زبان و خروج را باز می‌کند.
- **نشست:** پس از ۳۰ دقیقه بی‌فعالیتی، دوباره باید وارد شوید.
- **راهنما:** کنار عنوان بیشتر صفحه‌ها یک دکمه‌ی «؟» هست که مستقیم به راهنمای همان صفحه می‌آید. در این صفحه هم می‌توانید جستجو کنید.

@@article add-database /instances/new
@title افزودن پایگاه داده
@summary ثبت یک سرور MySQL یا MariaDB و آزمایش اتصال آن.
اول در کارت **سرور فعال**، سروری را که دیتابیس روی آن است انتخاب کنید؛ سپس از منوی **پایگاه‌های داده ← افزودن پایگاه داده**. دیتابیس روی همان سرور ثبت می‌شود (فرم نام سرور را نشان می‌دهد):

- روی **سرور خود پنل**، پنل خودش مستقیم به دیتابیس وصل می‌شود.
- روی **سرور دیگر**، agent همان سرور دیتابیس را تست، فهرست و بکاپ می‌کند؛ لازم نیست درگاه دیتابیس به بیرون باز باشد.

| فیلد                 | توضیح                                                                    |
| -------------------- | ------------------------------------------------------------------------ |
| نام                  | نامی دلخواه برای نمایش، مثلاً `prod` (در نام پوشه و فایل بکاپ هم می‌آید) |
| میزبان و درگاه       | نشانی دیتابیس؛ برای انتخاب درست [این راهنما](#db-host) را ببینید         |
| نام کاربری و گذرواژه | ترجیحاً یک [کاربر اختصاصی بکاپ](#backup-user)                            |
| یادداشت              | اختیاری                                                                  |

قبل از ذخیره **«آزمایش اتصال»** را بزنید. پنل نوع (MySQL یا MariaDB) و نسخه را تشخیص می‌دهد. اگر خطا گرفتید، [رفع خطاهای اتصال](#connection-errors) را ببینید.

> گذرواژه رمزنگاری‌شده ذخیره می‌شود و هیچ‌وقت دوباره نمایش داده نمی‌شود. هنگام ویرایش، اگر فیلد گذرواژه را خالی بگذارید همان قبلی حفظ می‌شود.

@@article db-host
@title چه نشانی‌ای برای میزبان وارد کنم؟
@summary انتخاب درست Host و Port برای دیتابیس داخل کانتینر، روی خود سرور یا روی سرور دیگر.
پنل خودش داخل کانتینر اجرا می‌شود؛ پس `localhost` و `127.0.0.1` یعنی **خود پنل**، نه سرور شما.

## دیتابیس داخل یک کانتینر Docker (روی همین سرور)

کانتینر دیتابیس را به شبکه‌ی پنل وصل کنید:

```bash
docker network connect mbp-net <db-container>
```

سپس میزبان = **نام کانتینر** (مثلاً `mysql_db`) و درگاه = **درگاه داخلی** (معمولاً `3306`)، نه درگاهی که روی سرور منتشر شده.

برای اینکه با ساخت دوباره‌ی کانتینر این اتصال از بین نرود، در compose همان پروژه بنویسید:

```yaml
services:
  mysql_db:
    networks: [default, mbp-net]
networks:
  mbp-net:
    external: true
```

## دیتابیس نصب‌شده مستقیم روی همین سرور

میزبان = `host.docker.internal` و درگاه سرور. دیتابیس باید روی نشانی‌ای گوش کند که از کانتینرها قابل دسترسی است (اگر `bind-address` روی `127.0.0.1` است، در دسترس نیست).

## دیتابیس روی یک سرور دیگر

- **پیشنهادی:** آن سرور را [به پنل وصل کنید](#add-server)، در کارت سرور فعال آن را انتخاب کنید و دیتابیس را همان‌جا اضافه کنید. در این حالت میزبان از دید همان سرور است: `127.0.0.1` برای دیتابیسی که روی خود آن سرور منتشر شده، یا **نام کانتینر** برای دیتابیسی که در کانتینر است. لازم نیست درگاه دیتابیس را به بیرون باز کنید.
- **مستقیم:** روی سرور خود پنل یک دیتابیس اضافه کنید و نشانی IP یا دامنه و درگاه سرور دیگر را وارد کنید؛ فایروال آن سرور باید اتصال از این سرور را بپذیرد.

@@article backup-user
@title کاربر اختصاصی برای بکاپ
@summary ساخت کاربری با کمترین دسترسی لازم به‌جای root.
به‌جای `root` یک کاربر مخصوص بسازید:

```bash
docker exec -it <db-container> mysql -uroot -p
```

```sql
CREATE USER 'mbp_backup'@'%' IDENTIFIED BY 'a-strong-password';
GRANT SELECT, SHOW VIEW, TRIGGER, EVENT, LOCK TABLES ON *.* TO 'mbp_backup'@'%';
FLUSH PRIVILEGES;
```

- برای MariaDB به‌جای `mysql` از `mariadb` استفاده کنید.
- دسترسی `PROCESS` لازم نیست.
- پنل فقط دیتابیس‌هایی را فهرست می‌کند که این کاربر می‌بیند؛ اگر دیتابیسی در فهرست نیست، دسترسی‌های کاربر را بررسی کنید.

@@article select-databases /instances
@title انتخاب دیتابیس‌ها برای بکاپ
@summary کدام دیتابیس‌ها در «بکاپ همه» و زمان‌بندی‌ها گرفته شوند.
در صفحه‌ی هر پایگاه داده، بخش **«پایگاه‌های داده برای پشتیبان‌گیری»** فهرست دیتابیس‌های سرور را نشان می‌دهد.

- دیتابیس‌های مورد نظر را تیک بزنید و **«ذخیره‌ی انتخاب»** را بزنید.
- «بکاپ از همه» و زمان‌بندی‌های «همه‌ی علامت‌خورده‌ها» فقط همین‌ها را بکاپ می‌گیرند.
- شماهای سیستمی (`information_schema`، `performance_schema`، `sys`) قابل انتخاب نیستند؛ با کلید «نمایش شماهای سیستمی» دیده می‌شوند.
- اگر دیتابیسی انتخاب‌شده دیگر روی سرور نباشد، با برچسب «روی سرور وجود ندارد» نشان داده می‌شود؛ تیکش را بردارید.
- بکاپ تکی از یک دیتابیس نیازی به علامت خوردن ندارد.

@@article connection-errors
@title رفع خطاهای اتصال
@summary معنی هر خطای آزمایش اتصال و راه‌حل آن.

| خطا                 | علت معمول                                                        | راه‌حل                                                                 |
| ------------------- | ---------------------------------------------------------------- | ---------------------------------------------------------------------- |
| میزبان پیدا نشد     | نام اشتباه، یا نام کانتینری که به شبکه‌ی پنل وصل نیست            | املای نام؛ `docker network connect mbp-net …`                          |
| اتصال رد شد         | درگاه اشتباه، یا سرویس روی آن نشانی گوش نمی‌کند                  | درگاه داخلی کانتینر (3306) را بزنید، نه درگاه منتشرشده؛ `bind-address` |
| زمان پاسخ تمام شد   | فایروال یا مسیر شبکه                                             | فایروال سرور دیتابیس و دسترسی از سرور پنل                              |
| اطلاعات ورود رد شد  | نام کاربری/گذرواژه، یا کاربر اجازه‌ی اتصال از این نشانی را ندارد | کاربر را با `'%'` بسازید ([راهنما](#backup-user))                      |
| agent در دسترس نیست | برای دیتابیس‌های سرورهای دیگر: agent آن سرور خاموش است           | [رفع اشکال سرورها](#server-troubleshoot)                               |

> هنگام ویرایش، اگر میزبان یا کاربر را عوض کرده‌اید، برای آزمایش باید گذرواژه را هم دوباره وارد کنید.

@@article manual-backup /instances
@title بکاپ دستی
@summary گرفتن بکاپ فوری از همه‌ی دیتابیس‌های علامت‌خورده یا از یک دیتابیس.
در صفحه‌ی هر پایگاه داده، بخش **پشتیبان‌ها**:

- **«پشتیبان‌گیری از همه‌ی پایگاه‌های داده‌ی انتخاب‌شده»**: برای هر دیتابیس علامت‌خورده یک بکاپ جدا.
- **«پشتیبان‌گیری از یک پایگاه داده»**: هر دیتابیسی، حتی اگر علامت نخورده باشد.

پیشرفت (حجم خروجی و زمان) همان‌جا و در [پشتیبان‌ها](/backups) دیده می‌شود. چند بکاپ هم‌زمان اجرا می‌شوند (پیش‌فرض ۲) و بقیه در صف می‌مانند. دو بکاپ از یک دیتابیس هیچ‌وقت هم‌زمان اجرا نمی‌شوند.

از ربات هم می‌شود بکاپ گرفت؛ [کار با ربات](#bots-usage) را ببینید.

@summary مراحل ساخت فایل و تضمین سالم بودن آن.

1. پنل به سرور وصل می‌شود و نوع آن (MySQL یا MariaDB) را تشخیص می‌دهد.
2. ابزار مناسب (`mysqldump` برای MySQL و `mariadb-dump` برای MariaDB) با این گزینه‌ها اجرا می‌شود: `--single-transaction --quick --routines --triggers --events --hex-blob --no-tablespaces`. بنابراین جدول‌ها قفل نمی‌شوند و view، procedure، trigger و event هم در بکاپ هستند.
3. گذرواژه فقط در یک فایل موقت خصوصی به ابزار داده می‌شود و هیچ‌وقت در خط فرمان یا لاگ دیده نمی‌شود.
4. خروجی هم‌زمان فشرده و در یک فایل موقت نوشته می‌شود؛ پس دیتابیس‌های بزرگ هم حافظه را پر نمی‌کنند.
5. فایل **بررسی** می‌شود: checksum از نوع SHA-256، باز شدن کامل فایل فشرده، و وجود نشانه‌ی پایان `-- Dump completed`.
6. فقط بعد از این بررسی‌ها فایل نام نهایی می‌گیرد. بکاپ ناموفق یا نیمه‌کاره هیچ فایلی باقی نمی‌گذارد و علت خطا نمایش داده می‌شود.

برای دیتابیس‌هایی که «از طریق سرور» تعریف شده‌اند، مرحله‌ی ۲ روی همان سرور توسط agent انجام می‌شود و خروجی به پنل منتقل و همین‌جا فشرده و بررسی می‌شود.

@@article history /backups
@title تاریخچه، دانلود و حذف
@summary کار با صفحه‌ی پشتیبان‌ها.
صفحه‌ی [پشتیبان‌ها](/backups) همه‌ی اجراها را نشان می‌دهد: وضعیت، حجم، مدت، checksum، نوع اجرا (دستی، زمان‌بندی، قبل از دیپلوی) و وضعیت آپلود ابری.

- **فیلتر و مرتب‌سازی:** بر اساس سرور، نام دیتابیس، وضعیت و بازه‌ی تاریخ.
- **دانلود:** اگر فایل محلی حذف شده ولی نسخه‌ی ابری هست، پنل فایل را از فضای ابری برایتان می‌فرستد.
- **حذف:** به‌صورت پیش‌فرض فقط فایل روی سرور پاک می‌شود و نسخه‌ی ابری و رکورد در تاریخچه می‌مانند. برای حذف نسخه‌ی ابری، گزینه‌ی «نسخه‌ی ابری هم حذف شود» را بزنید ([محافظت ۷ روزه](#remote-protection)).
- **بارگذاری دوباره:** اگر آپلود ناموفق بود، «تلاش دوباره برای آپلود» را بزنید.
- **جزئیات خطا:** روی بکاپ ناموفق بزنید تا علت و راه‌حل پیشنهادی را ببینید.

@@article backup-settings /settings/backups
@title پوشه، نام فایل و فشرده‌سازی
@summary تنظیمات سراسری بکاپ و تنظیم اختصاصی هر پایگاه داده.
در **ذخیره‌سازی و نگهداری ← تنظیمات پشتیبان‌گیری**:

- **پوشه‌ی ذخیره:** نسبت به محل ذخیره‌ی بکاپ‌ها (volume `mbp-backups`).
- **الگوی نام فایل:** پیش‌فرض `{instance}/{database}_{date}_{time}`. جای‌نگهدارها: `{instance}` `{database}` `{date}` `{time}` `{datetime}` `{server_type}`. علامت `/` زیرپوشه می‌سازد، زمان‌ها UTC هستند و پسوند خودکار اضافه می‌شود.
- **فشرده‌سازی:** gzip (پیش‌فرض)، bzip2 یا بدون فشرده‌سازی.

هر پایگاه داده در صفحه‌ی خودش می‌تواند هر کدام را جداگانه تغییر دهد. تغییرات فقط روی بکاپ‌های جدید اثر دارند.

فایل‌ها داخل کانتینر در `/backups` هستند:

```bash
docker compose exec backend find /backups -type f
```

@title زمان‌بندی خودکار
@summary بکاپ خودکار با cron و منطقه‌ی زمانی.
در [زمان‌بندی‌ها](/schedules) یا صفحه‌ی هر پایگاه داده، **«افزودن زمان‌بندی»**:

- **تناوب:** گزینه‌های آماده (هر ساعت، روزانه، هفتگی، ماهانه) یا عبارت cron سفارشی با ۵ بخش: `دقیقه ساعت روزِماه ماه روزِهفته`.
- **منطقه‌ی زمانی:** مثلاً `Asia/Tehran`. فرم پنج اجرای بعدی را نشان می‌دهد تا مطمئن شوید.
- **از چه چیزی:** همه‌ی دیتابیس‌های علامت‌خورده، یا یک دیتابیس.

| مثال cron     | معنی                      |
| ------------- | ------------------------- |
| `30 1 * * *`  | هر روز ساعت ۰۱:۳۰         |
| `0 */6 * * *` | هر ۶ ساعت                 |
| `0 3 * * 6`   | شنبه‌ها ساعت ۰۳:۰۰        |
| `0 2 1 * *`   | روز اول هر ماه ساعت ۰۲:۰۰ |

- نتیجه‌ی آخرین اجرا کنار هر زمان‌بندی نمایش داده می‌شود (مثلاً «پایگاه داده‌ای علامت نخورده»).
- اگر پنل هنگام زمان اجرا خاموش بوده باشد و تا ۵ دقیقه بعد روشن شود، اجرا انجام می‌شود؛ وگرنه تا نوبت بعد صبر می‌کند.
- اگر بکاپ قبلی همان دیتابیس هنوز در حال اجرا باشد، آن دیتابیس این دور رد می‌شود.

@@article restore
@title بازگردانی بکاپ
@summary برگرداندن فایل بکاپ به یک دیتابیس.
فایل را از [پشتیبان‌ها](/backups) دانلود کنید و در یک دیتابیس **خالی** بازگردانید:

```bash
gunzip -c shop_2026-10-11_140804.sql.gz | mysql -h HOST -u root -p shop     # MySQL
gunzip -c shop_2026-10-11_140804.sql.gz | mariadb -h HOST -u root -p shop   # MariaDB
```

- برای فایل bzip2 از `bunzip2 -c` و برای فایل بدون فشرده‌سازی از `cat` استفاده کنید.
- دیتابیس مقصد را قبلاً بسازید: `CREATE DATABASE shop;`.
- چون فایل `CREATE DATABASE` و `USE` ندارد، می‌توانید با نام دیگری بازگردانی کنید؛ مثلاً برای امتحان روی `shop_test`.
- اگر فقط نسخه‌ی ابری باقی مانده، دانلود از پنل همان را می‌آورد؛ یا با هر کلاینت S3 مثل `aws s3 cp` بگیرید.

> ! قبل از بازگردانی روی دیتابیس اصلی، یک بار روی دیتابیس آزمایشی امتحان کنید.

@@article remote-storage /settings/backups
@title اتصال به فضای ابری (S3)
@summary آپلود خودکار بکاپ‌ها در AWS S3 یا هر سرویس سازگار.
در **ذخیره‌سازی و نگهداری ← فضای راه دور** اطلاعات زیر را وارد کنید:

| فیلد           | توضیح                                                                               |
| -------------- | ----------------------------------------------------------------------------------- |
| نشانی Endpoint | برای AWS خالی؛ برای بقیه نشانی سرویس، مثلاً `https://s3.ir-thr-at1.arvanstorage.ir` |
| ناحیه          | مثلاً `ir-thr-at1` یا `us-east-1`                                                   |
| باکت           | فقط نام باکت، بدون `s3://` و اسلش                                                   |
| پیشوند کلید    | پوشه‌ای داخل باکت (اختیاری)                                                         |
| کلیدها         | Access key و Secret key                                                             |
| path-style     | برای MinIO، RustFS، Ceph و ابرآروان روشن باشد                                       |

1. **«آزمایش اتصال»** را بزنید؛ پنل نوشتن و پاک کردن در باکت را امتحان می‌کند.
2. **«بارگذاری نسخه‌های پشتیبان در فضای راه دور»** را روشن و ذخیره کنید. بدون این کلید، حتی با اتصال موفق، چیزی آپلود نمی‌شود.
3. هر پایگاه داده در صفحه‌ی خودش می‌تواند «همیشه / هرگز / تنظیم سراسری» را انتخاب کند.

- آپلود بعد از بررسی سالم بودن بکاپ و تکه‌تکه (۶۴ مگابایتی) انجام می‌شود.
- آپلود ناموفق، بکاپ را خراب نمی‌کند: فایل محلی می‌ماند و می‌توانید دوباره تلاش کنید.
- کلید محرمانه رمزنگاری‌شده ذخیره و هیچ‌وقت دوباره نمایش داده نمی‌شود.

برای کمترین دسترسی، به کلید فقط `s3:PutObject`، `s3:GetObject`، `s3:DeleteObject` و `s3:ListBucket` روی همان باکت بدهید.

@@article arvancloud /settings/backups
@title راه‌اندازی ابرآروان قدم به قدم
@summary اتصال پنل به Object Storage ابرآروان.

1. در کنسول ابرآروان، **فضای ابری (Object Storage)** را باز و یک باکت **خصوصی** بسازید (مثلاً `airplus`).
2. در بخش **کلیدهای دسترسی** یک جفت کلید بسازید و Access key و Secret key را بردارید. کلید محرمانه فقط یک بار نمایش داده می‌شود.
3. نشانی Endpoint منطقه را از کنسول بردارید، مثلاً `https://s3.ir-thr-at1.arvanstorage.ir` (تهران). نام ناحیه بخش وسط آن است: `ir-thr-at1`.
4. در پنل، **ذخیره‌سازی و نگهداری ← فضای راه دور**:

| فیلد           | مقدار                                   |
| -------------- | --------------------------------------- |
| نشانی Endpoint | `https://s3.ir-thr-at1.arvanstorage.ir` |
| ناحیه          | `ir-thr-at1`                            |
| باکت           | `airplus`                               |
| پیشوند کلید    | `mysql-backup` (اختیاری)                |
| path-style     | روشن                                    |

5. «آزمایش اتصال» باید موفق شود.
6. کلید «بارگذاری نسخه‌های پشتیبان…» را روشن و **ذخیره** کنید.
7. یک بکاپ بگیرید؛ در تاریخچه وضعیت «ذخیره در فضای ابری» را می‌بینید و فایل با همان مسیر و نام در باکت قرار می‌گیرد.

> ! کلید محرمانه را هرگز در چت، تیکت یا پیام‌رسان نفرستید؛ فقط مستقیم در پنل وارد کنید. اگر جایی فاش شد، در کنسول ابرآروان آن را باطل کنید و کلید جدید بسازید.

نشانی‌ای مثل `s3://airplus/mysql-backup/` یعنی باکت `airplus` و پیشوند `mysql-backup`.

@@article remote-protection
@title محافظت ۷ روزه‌ی نسخه‌های ابری
@summary چرا نسخه‌های ابری تا ۷ روز پس از آپلود از پنل حذف نمی‌شوند.
پنل یک نسخه‌ی ابری را تا **۷ روز پس از آپلود** حذف نمی‌کند؛ نه با سیاست نگهداری و نه به‌صورت دستی. این از نسخه‌های بیرون از سرور در برابر اشتباه، یا کسی که به پنل دسترسی پیدا کرده، محافظت می‌کند.

- در این ۷ روز، گزینه‌ی «نسخه‌ی ابری هم حذف شود» غیرفعال است و تاریخ آزاد شدن را نشان می‌دهد.
- اگر واقعاً لازم است، از کنسول خود فضای ابری (مثلاً ابرآروان) حذف کنید.
- حداقل «حذف پس از» برای نسخه‌های ابری در سیاست نگهداری ۷ روز است.

> برای محافظتی که حتی اگر خود پنل هم در اختیار کسی قرار گرفت پابرجا بماند، در سرویس ذخیره‌سازی _Object Lock_ یا قانون lifecycle/retention روی باکت فعال کنید.

@@article retention /settings/backups
@title سیاست نگهداری (پاکسازی خودکار)
@summary حذف خودکار بکاپ‌های قدیمی برای پر نشدن دیسک و فضای ابری.
در **ذخیره‌سازی و نگهداری ← سیاست نگهداری**، برای **فایل‌های محلی** و **نسخه‌های ابری** جداگانه:

- **نگه‌داشتن آخرین N** بکاپ برای هر دیتابیس.
- **حذف پس از N روز**.

نکات مهم:

- فیلد خالی یعنی بدون محدودیت. اگر هر دو را تعیین کنید، بکاپی که یکی از آن‌ها را نقض کند حذف می‌شود.
- **جدیدترین بکاپ هر دیتابیس هرگز حذف نمی‌شود**، حتی اگر قدیمی‌تر از محدودیت باشد.
- فقط بکاپ‌های موفق شامل می‌شوند.
- نسخه‌های ابری کمتر از ۷ روزه حذف نمی‌شوند ([چرا؟](#remote-protection)).
- بعد از هر بکاپ (برای همان دیتابیس) و هر ساعت برای همه اجرا می‌شود.
- **«پیش‌نمایش و اجرای فوری»** قبل از حذف، فهرست فایل‌هایی را که حذف می‌شوند نشان می‌دهد.
- هر پایگاه داده در صفحه‌ی خودش می‌تواند سیاست جداگانه داشته باشد.

رکورد بکاپ در تاریخچه می‌ماند و نشان می‌دهد فایل کِی و چرا حذف شده است.

@title اعلان‌ها و قوانین
@summary کدام رویدادها خبر داده شوند و به کجا.
در [اعلان‌ها](/notifications) برای هر رویداد تعیین می‌کنید روشن باشد یا نه و به کدام کانال‌ها (بله، تلگرام، وب‌هوک) برود.

| رویداد                                                                | اهمیت       |
| --------------------------------------------------------------------- | ----------- |
| بکاپ ناموفق، آپلود ناموفق                                             | خطا         |
| بکاپ اخیر وجود ندارد (پیش‌فرض بیش از ۲۶ ساعت)                         | خطا         |
| فضای دیسک کم (پیش‌فرض کمتر از ۱۰٪)                                    | هشدار       |
| زمان‌بندی اجرا نشد، سیاست نگهداری نتوانست حذف کند                     | هشدار       |
| کانتینر از کار افتاد، حلقه‌ی ری‌استارت، ناسالم، مصرف بالا، منابع سرور | خطا / هشدار |
| agent در دسترس نیست، دیپلوی ناموفق                                    | خطا         |
| بکاپ موفق، دیپلوی موفق، رفع مشکل، خلاصه‌ی روزانه                      | اطلاع       |

- **فاصله‌ی تکرار (cooldown):** یک هشدار تکراری درباره‌ی یک چیز حداکثر یک بار در هر دوره (پیش‌فرض ۶۰ دقیقه) فرستاده می‌شود.

- **خلاصه‌ی روزانه** در ساعتی که تعیین می‌کنید.
- **تاریخچه:** همه‌ی هشدارها ۹۰ روز با محل ارسال نگه داشته می‌شوند.
- **«ارسال هشدار آزمایشی»** همه‌ی کانال‌ها را با هم امتحان می‌کند.

هشدارهای سرورهای دیگر با نام همان سرور شروع می‌شوند.

@@article webhook /notifications
@title وب‌هوک امضاشده
@summary ارسال هشدارها به سیستم‌های دیگر با امضای HMAC.
در [اعلان‌ها](/notifications) نشانی وب‌هوک و در صورت تمایل یک **رمز امضا** وارد کنید. هر هشدار به‌صورت JSON با POST فرستاده می‌شود:

```json
{
  "event": "backup_failed",
  "severity": "error",
  "subject": "backup_failed:1:shop",
  "message": "...",
  "params": {},
  "run_id": 42,
  "created_at": "2026-10-11T08:00:00+00:00",
  "source": "mysql-backup-panel"
}
```

با رمز امضا، هدر `X-MBP-Signature` برابر `sha256=` و سپس HMAC-SHA256 بدنه‌ی درخواست است؛ گیرنده با همان رمز می‌تواند بررسی کند که پیام واقعاً از پنل آمده است.

@@article bots-setup /bots
@title راه‌اندازی ربات بله و تلگرام
@summary ساخت ربات، وارد کردن توکن و ثبت مدیران.
ربات از سمت پنل به پیام‌رسان وصل می‌شود (long polling)؛ پس پنل به نشانی عمومی یا پورت باز نیاز ندارد.

1. در **بله** به `@botfather` بروید (در **تلگرام** `@BotFather` و دستور `/newbot`)، ربات بسازید و توکن را بردارید.
2. در [ربات‌ها](/bots) ربات را روشن کنید، توکن را وارد کنید، **«آزمایش توکن»** و سپس **ذخیره** را بزنید. وقتی اجرا شود، برچسب «متصل با نام @…» نمایش داده می‌شود.
3. در **مدیران ربات** افرادی را که اجازه دارند ثبت کنید، به یکی از دو روش:
   - **شناسه‌ی عددی:** اگر شخص به ربات پیام بدهد، ربات شناسه‌اش را جواب می‌دهد.
   - **کد اتصال:** «ساخت کد اتصال» را بزنید؛ شخص کد را ظرف ۱۵ دقیقه برای ربات بفرستد و خودکار ثبت می‌شود.

> اگر تلگرام روی سرور فیلتر است، در «تنظیمات پیشرفته» یک پراکسی `http://`، `https://` یا `socks5://` (بدون نام کاربری و رمز) وارد کنید.

@title کار با ربات
@summary کارهایی که از داخل بله و تلگرام می‌شود انجام داد.
با `/start` (یا `/menu`) منوی ربات باز می‌شود که مثل منوی پنل گروه‌بندی شده است:

- **📊 نمای کلی:** پایگاه‌های داده، بکاپ‌های در حال اجرا، ۲۴ ساعت گذشته، فضای دیسک، اجرای بعدی، سرورهای متصل و استقرارهای ناموفق.

- **🗄 پایگاه داده و بکاپ ← آخرین بکاپ‌ها:** تاریخچه، جزئیات، تلاش دوباره برای آپلود، حذف (با تأیید)، و دریافت فایل اگر اجازه داده باشید.
- **🗄 پایگاه داده و بکاپ ← زمان‌بندی‌ها:** روشن، خاموش، اجرای فوری.
- **🗄 پایگاه داده و بکاپ ← سیاست نگهداری:** پیش‌نمایش و اجرا.
- **🚀 پروژه‌ها:** آخرین استقرارها و استقرار با کد Google Authenticator.
- **🐳 کانتینرها:** وضعیت، مصرف، لاگ (اگر اجازه داده باشید)، و شروع/توقف/ری‌استارت با کد Google Authenticator. اگر چند سرور دارید، اول سرور را انتخاب می‌کنید.
- **🖥 سرورها:** وضعیت هر سرور، همراه با کانتینرها، منابع (CPU، RAM، دیسک)، پروژه‌ها و پایگاه‌های داده‌ی آن.
- **⚙️ هشدارها و زبان:** سطح هشدارهای خودتان (همه، هشدار و خطا، فقط خطا، خاموش) و زبان.
- **❓ راهنما:** کار هر بخش و فهرست دستورها.

دستورها (در منوی دستورهای پیام‌رسان هم دیده می‌شوند): `/menu`، `/status`، `/backups`، `/projects`، `/containers`، `/servers`، `/settings`، `/help`.

- توکن ربات رمزنگاری‌شده ذخیره می‌شود و هر کار ربات با شناسه‌ی مدیر در لاگ ثبت می‌شود.

@@article current-server
@title سرور فعال و تغییر سرور
@summary پنل همیشه روی یک سرور کار می‌کند؛ از کارت پایین منو آن را عوض کنید.
پنل همیشه روی **یک سرور** کار می‌کند: «سرور فعال». نام و وضعیت آن در کارت پایین منوی کناری دیده می‌شود (در موبایل، دکمه‌ی نام سرور بالای صفحه). روی کارت بزنید تا:

- **سرور دیگری را انتخاب کنید.** سرورهایی که هنوز وصل نشده‌اند قابل انتخاب نیستند.
- به **«مدیریت همه‌ی سرورها»** بروید: افزودن، اتصال، ویرایش و حذف سرورها.

## چه چیزهایی به سرور فعال بستگی دارد؟

| فقط سرور فعال        | برای همه‌ی سرورها مشترک            |
| -------------------- | ---------------------------------- |
| پایگاه‌های داده      | اعلان‌ها و هشدارها                 |
| پشتیبان‌ها (تاریخچه) | ربات‌های بله و تلگرام              |
| زمان‌بندی‌ها         | تنظیمات (بکاپ، فضای ابری، نگهداری) |
| کانتینرها            | حساب کاربری                        |
| پروژه‌ها             | راهنما                             |

- نام سرور فعال کنار عنوان صفحه‌های وابسته به سرور هم نمایش داده می‌شود.
- هر چیزی که اضافه می‌کنید (پایگاه داده، پروژه) روی سرور فعال ثبت می‌شود.
- انتخاب شما در همین مرورگر ذخیره می‌شود. اگر آن سرور حذف یا قطع شود، پنل به سرور خودش برمی‌گردد.
- مثال: برای کار با کانتینرهای سرور دوم، اول در کارت سرور فعال آن را انتخاب کنید، سپس به [کانتینرها](/containers) بروید.

@@article servers-overview /servers
@title مدیریت چند سرور
@summary یک پنل برای چند ماشین: کانتینرها، پروژه‌ها و دیتابیس‌های همه‌ی سرورها.
پنل همیشه **سرور خودش** (با برچسب «همین سرور») را دارد. هر سرور دیگری با نصب یک **agent** کوچک به پنل وصل می‌شود. پس از اتصال، با انتخاب آن در [کارت سرور فعال](#current-server):

- **کانتینرها** همان سرور را می‌بینید. تنظیمات و هشدارها برای هر سرور جداست.
- **پروژه‌ها** روی همان سرور دیپلوی می‌شوند.
- **پایگاه‌های داده** را agent همان سرور تست، فهرست و بکاپ می‌کند؛ لازم نیست درگاه دیتابیس را به بیرون باز کنید.
- **هشدارها و ربات:** نام سرور در هشدارها می‌آید و ربات اول سرور را می‌پرسد.

صفحه‌ی **مدیریت همه‌ی سرورها** از کارت سرور فعال باز می‌شود. کارت هر سرور وضعیت (متصل، در دسترس نیست، وصل نشده)، نام میزبان، نسخه‌ی Docker، آخرین ارتباط، اثر انگشت گواهی و تعداد پروژه‌ها و دیتابیس‌هایش را نشان می‌دهد.

@@article add-server /servers
@title افزودن سرور جدید
@summary نصب agent روی سرور دیگر و وصل کردن آن به پنل.
پیش‌نیاز روی سرور جدید: **Docker** با **Compose v2**.

1. از منو **سرورها** را باز کنید (یا روی کارت سرور فعال و سپس **«مدیریت همه‌ی سرورها»** بزنید) و سپس **«افزودن سرور»** را بزنید: نام، نشانی IP یا دامنه‌ای که پنل با آن به سرور می‌رسد، و درگاه agent (پیش‌فرض `8443`).
2. پنل دستورهای نصب را با یک **توکن مخصوص این سرور** نشان می‌دهد. **توکن فقط همین یک بار نمایش داده می‌شود.** دستورها را کپی کنید و روی سرور جدید اجرا کنید:

```bash
git clone https://github.com/malekipourdev/database-backup-manager.git mbp-agent && cd mbp-agent
cat > .env.agent <<EOF
MBP_AGENT_TOKEN=<TOKEN>
MBP_AGENT_PORT=8443
MBP_DOCKER_GID=$(stat -c %g /var/run/docker.sock)
EOF
sudo mkdir -p /opt/mbp-projects && sudo chown 10001:10001 /opt/mbp-projects
docker compose -f docker-compose.agent.yml --env-file .env.agent up -d --build
```

3. درگاه agent را در فایروال **فقط برای IP سرور پنل** باز کنید:

```bash
sudo ufw allow from <PANEL-IP> to any port 8443 proto tcp
```

4. در پنل **«اتصال»** را بزنید. اگر موفق شد، وضعیت «متصل» می‌شود.
5. برای کار روی سرور جدید، روی کارتش **«کار روی این سرور»** را بزنید یا آن را از کارت سرور فعال انتخاب کنید.

> اگر مخزن خصوصی است، روی سرور جدید هم مثل نصب پنل با دسترسی خودتان clone کنید. اگر توکن را گم کردید، از «توکن جدید» استفاده کنید.

@title امنیت اتصال سرورها
@summary پنل چطور مطمئن می‌شود با agent واقعی صحبت می‌کند.

- agent در اولین اجرا یک گواهی HTTPS برای خودش می‌سازد (در volume `mbp-agent-data` نگه داشته می‌شود).

- توکن در پنل رمزنگاری‌شده ذخیره می‌شود.
- agent رمز دیتابیس‌ها را ذخیره نمی‌کند؛ پنل برای هر کار، آن را از همین اتصال امن می‌فرستد.
- agent کارهای محدود و مشخصی بلد است، مقدار متغیرهای محیطی کانتینرها را برنمی‌گرداند و با فایل‌سیستم فقط‌خواندنی و بدون capability اجرا می‌شود.

> ساعت پنل و سرورها باید با هم تنظیم باشد (اختلاف کمتر از ۵ دقیقه)؛ NTP را روشن نگه دارید.

## به‌روزرسانی agent

روی همان سرور، در پوشه‌ی `mbp-agent`:

```bash
git pull
docker compose -f docker-compose.agent.yml --env-file .env.agent up -d --build
```

گواهی در volume می‌ماند، پس نیازی به اتصال دوباره نیست.

## توکن جدید

اگر توکن فاش شد یا گم شد، در کارت سرور «توکن جدید» را بزنید. توکن قبلی فوراً از کار می‌افتد. توکن جدید را در `.env.agent` بگذارید، دستور `up -d` بالا را دوباره اجرا کنید و «اتصال» را بزنید.

## حذف سرور

- تا وقتی پروژه یا دیتابیسی روی سرور تعریف شده، حذف ممکن نیست؛ اول آن‌ها را حذف یا جابه‌جا کنید.
- حذف از پنل، agent را از روی سرور پاک نمی‌کند. روی آن سرور اجرا کنید: `docker compose -f docker-compose.agent.yml down -v`
- سرور خود پنل قابل حذف نیست، ولی می‌توانید نامش را عوض کنید.

@@article webservers /webservers
@title وب‌سرورها (nginx و Apache)
@summary دامنه‌ها، وضعیت، reload، لاگ‌ها، حالت تعمیر و سایت جدید روی nginx یا Apache یک سرور.

صفحه‌ی **وب‌سرورها** (در بخش مدیریت سرور) nginx و Apache سرور فعلی و همه‌ی دامنه‌هایشان را نشان می‌دهد و امکان مدیریتشان را می‌دهد.

## اجزای صفحه

- **کارت وضعیت:** در حال اجرا بودن یا نبودن، نسخه، از چه زمانی، آخرین reload. **تست پیکربندی** دستور `nginx -t` / `apachectl configtest` را اجرا می‌کند؛ **Reload** و **ری‌استارت** فقط بعد از تست موفق انجام می‌شوند.
- **دامنه‌ها:** پورت‌ها، HTTPS همراه روزهای باقی‌مانده‌ی گواهی، آنچه دامنه سرو می‌کند (پراکسی، PHP-FPM، انتقال یا پوشه)، فایل و شماره‌ی خط. سایت‌های غیرفعال زیر «همه» هستند. یک نقطه وضعیت پایش سلامت را نشان می‌دهد.
- **با کلیک روی دامنه** پنل آن باز می‌شود: پیکربندی، لاگ‌ها، نسخه‌های قبلی و دکمه‌های زیر.

## دکمه‌های هر سایت

- **غیرفعال / فعال کردن:** لینک `sites-enabled` را برمی‌دارد یا می‌سازد (Debian، Ubuntu)، یا فایل `conf.d` را به `….mbp-disabled` تغییر نام می‌دهد و برعکس. فایل روی دیسک می‌ماند.
- **حالت تعمیر:** بازدیدکننده‌ها با همان نام‌ها، پورت‌ها و گواهی، صفحه‌ی 503 «در حال تعمیر» می‌بینند؛ **پایان تعمیر** سایت را دقیقاً همان‌طور که بود برمی‌گرداند.
- **گرفتن / تمدید گواهی SSL** و **پایش این سایت**: [گواهی‌ها](#webservers-ssl) و [پایش سلامت](#webservers-checks) را ببینید.
- **لاگ‌ها:** لاگ دسترسی و خطای سایت، ۱۰۰ تا ۲۰۰۰ خط آخر.

## سایت جدید

**سایت جدید** از روی یک قالب سایت می‌سازد — پراکسی معکوس (به یک آدرس یا پورت منتشرشده‌ی یک کانتینر)، PHP از طریق PHP-FPM، فایل‌های ثابت یا انتقال — فعالش می‌کند، تست و reload می‌کند. اگر تست شکست بخورد، دوباره حذف می‌شود. HTTPS را بعد با Let's Encrypt اضافه کنید.

یک [پروژه](#add-project) هم می‌تواند خودش این کار را بکند: دامنه‌ها و آدرس برنامه را در آن وارد کنید تا بعد از هر استقرار موفق، برای دامنه‌هایی که سایت ندارند یک سایت پراکسی ساخته شود.

## روشن کردن

این صفحه از agent استفاده می‌کند ([کانتینرها](#containers-enable) را ببینید). بعد از به‌روزرسانی پنل:

```bash
git pull
docker compose up -d --build agent
```

روی سرورهای دیگر، agent را مثل [به‌روزرسانی agent](#server-maintenance) دوباره build کنید.

@@article webservers-edit /webservers
@title ویرایش امن پیکربندی
@summary از هر تغییر نسخه‌ی پشتیبان گرفته، تست و در صورت خطا برگردانده می‌شود.

## با زدن ذخیره چه می‌شود

1. از فایل فعلی در `/var/backups/mbp-webserver` روی سرور یک نسخه گرفته می‌شود (۲۰ نسخه‌ی آخر نگه داشته می‌شود).
2. محتوای جدید نوشته می‌شود.
3. پیکربندی تست می‌شود (`nginx -t` یا `apachectl configtest`).
4. وب‌سرور reload می‌شود.

اگر مرحله‌ی ۳ یا ۴ شکست بخورد، فایل قبلی برگردانده می‌شود (و وب‌سرور دوباره reload می‌شود): هیچ پیکربندی خرابی روی دیسک نمی‌ماند. پنل پیام خود وب‌سرور را نشان می‌دهد، مثلاً فایل و خط یک اشتباه تایپی.

## خوب است بدانید

- اگر از وقتی فایل را باز کرده‌اید کسی آن را تغییر داده باشد، ذخیره رد می‌شود؛ دوباره بازش کنید.
- **نسخه‌های قبلی** نسخه‌ها را نشان می‌دهد و **بازگردانی** یکی از آن‌ها را به همین روش امن برمی‌گرداند.
- فقط فایل‌های داخل `/etc/nginx`، `/etc/apache2` یا `/etc/httpd` باز یا نوشته می‌شوند.
- **فعالیت‌ها** هر تغییر، انجام‌دهنده و خروجی آن را نشان می‌دهد؛ **تنظیمات ← فقط‌خواندنی** همه‌ی تغییرها را برای یک سرور خاموش می‌کند.

> agent تغییرها را با یک کانتینر کمکی کوتاه‌عمر روی سرور انجام می‌دهد که یک دستور ثابت را اجرا می‌کند و حذف می‌شود. پنل هیچ‌وقت دستور نمی‌فرستد، فقط نوع عملیات و مقادیر بررسی‌شده را.

@@article webservers-ssl /webservers
@title گواهی‌ها (Let's Encrypt)
@summary گواهی رایگان با certbot، تمدید خودکار و هشدار پیش از انقضا.

## گرفتن گواهی

1. دامنه باید در DNS به همین سرور اشاره کند و پورت ۸۰ از اینترنت در دسترس باشد.
2. دامنه را باز کنید و **گرفتن گواهی SSL** را بزنید. certbot از Let's Encrypt گواهی می‌گیرد، آن را به سایت اضافه می‌کند و (به انتخاب شما) بازدیدکننده‌های HTTP را به HTTPS می‌فرستد.
3. پیشرفت کار و خروجی certbot در همان پنجره و بعداً در **فعالیت‌ها** دیده می‌شود.

اگر certbot نصب نیست، کارت **Let's Encrypt** آن را نصب می‌کند (apt، dnf یا yum). گواهی wildcard (`*.example.com`) به چالش DNS نیاز دارد و اینجا پشتیبانی نمی‌شود.

## تمدید و هشدار

certbot خودش گواهی‌ها را تمدید می‌کند (`certbot.timer` یا cron؛ کارت نشان می‌دهد کدام). **تمدید همین حالا** فوراً `certbot renew` را اجرا می‌کند. پنل چند بار در روز گواهی همه‌ی سایت‌ها را می‌خواند؛ گواهی‌ای که تا ۱۴ روز دیگر (تنظیمات) منقضی شود به بله، تلگرام و وب‌هوک هشدار داده می‌شود و تمدیدش هم اطلاع داده می‌شود.

@title پایش سلامت
@summary پنل مرتب سایت‌ها را درخواست می‌کند و وقتی یکی پاسخ ندهد هشدار می‌دهد.

در **پایش سلامت** یک آدرس اضافه کنید یا روی یک دامنه **پایش این سایت** را بزنید. هر چند دقیقه یک بار (تنظیمات) پنل مثل یک بازدیدکننده آن را درخواست می‌کند و انتقال‌ها را دنبال می‌کند:

- پاسخ با کد کمتر از ۵۰۰ یعنی **بالا**؛ 5xx، نرسیدن پاسخ، برقرار نشدن اتصال یا خطای TLS یعنی خطا؛
- بعد از ۲ خطای پشت سر هم (تنظیمات) سایت **پایین** حساب و هشدار فرستاده می‌شود؛ وقتی دوباره پاسخ دهد، پیام برگشتن آن می‌آید؛
- جدول آخرین پاسخ، زمان پاسخ، دسترس‌پذیری ۲۴ ساعت گذشته و بررسی‌های اخیر را نشان می‌دهد.

> بررسی‌ها از سرور پنل انجام می‌شوند، پس نشان می‌دهند سایت شما از بیرون سروری که روی آن اجرا می‌شود هم در دسترس است یا نه.

@@article containers-enable /containers
@title روشن کردن مدیریت کانتینرها
@summary راه‌اندازی agent روی سرور خود پنل.
این بخش به‌صورت پیش‌فرض خاموش است و به یک کانتینر اضافه به نام **agent** نیاز دارد؛ تنها بخشی که به `docker.sock` دسترسی دارد. در پوشه‌ی پنل روی سرور:

```bash
echo "COMPOSE_PROFILES=containers" >> .env
echo "MBP_DOCKER_GID=$(stat -c %g /var/run/docker.sock)" >> .env
sudo mkdir -p /opt/mbp-projects && sudo chown 10001:10001 /opt/mbp-projects
docker compose up -d --build
```

- `MBP_DOCKER_GID` شناسه‌ی گروه سوکت Docker است تا agent اجازه‌ی استفاده از آن را داشته باشد. اگر پنل گفت agent اجازه‌ی استفاده از `docker.sock` را ندارد، همین مقدار را بررسی کنید.
- برای Docker بدون root یا Podman، `MBP_DOCKER_SOCKET` را هم روی مسیر سوکت بگذارید.
- برای خاموش کردن، خط `COMPOSE_PROFILES=containers` را از `.env` بردارید و `docker compose up -d --remove-orphans` را اجرا کنید.

> دسترسی به `docker.sock` معادل root روی سرور است؛ برای همین agent کوچک و محدود نگه داشته شده: درگاهی منتشر نمی‌کند، فقط به پنل جواب می‌دهد، دستور داخل کانتینرها اجرا نمی‌کند و کانتینرهای خود پنل را متوقف نمی‌کند.

@@article containers-usage /containers
@title کار با کانتینرها
@summary دیدن وضعیت، مصرف و لاگ و کنترل کانتینرها.

- **سرور:** کانتینرهای [سرور فعال](#current-server) نمایش داده می‌شوند؛ برای سرور دیگر، اول آن را در کارت سرور فعال انتخاب کنید.
- **زبانه‌ی کانتینرها:** همه‌ی کانتینرها گروه‌بندی‌شده بر اساس پروژه‌ی compose، مشکل‌دارها اول؛ وضعیت، سلامت، مدت اجرا یا کد خروج، CPU، RAM و تعداد ری‌استارت. هر ۵ ثانیه به‌روز می‌شود. بالای صفحه CPU، RAM و دیسک Docker سرور دیده می‌شود.
- **فیلتر و جستجو:** همه، در حال اجرا، مشکل‌دار، متوقف.
- **جزئیات (کلیک روی کانتینر):** ایمیج، درگاه‌ها، شبکه‌ها، volumeها، سیاست ری‌استارت، خروجی آخرین health check و **نام** متغیرهای محیطی (مقدارها هرگز نمایش داده نمی‌شوند).
- **لاگ:** ۱۰۰ تا ۵۰۰۰ خط آخر، stderr مشخص، با فیلتر، دنبال کردن زنده و دانلود.
- **شروع، توقف، ری‌استارت:** توقف و ری‌استارت تأیید می‌خواهند.
- **زبانه‌ی فعالیت‌ها:** هر شروع/توقف/ری‌استارت، از پنل یا ربات، توسط چه کسی و با چه نتیجه‌ای.

@@article containers-settings /containers
@title تنظیمات کانتینرها
@summary حالت فقط‌خواندنی، کانتینرهای مخفی و قفل، لاگ در ربات و آستانه‌های هشدار.
در زبانه‌ی **تنظیمات** (برای هر سرور جداگانه):

- **حالت فقط‌خواندنی:** فقط پایش؛ هیچ کانتینری از پنل یا ربات کنترل نمی‌شود.
- **کانتینرهای مخفی:** نام یا الگو (مثلاً `vault*`) که اصلاً نمایش داده نمی‌شوند.
- **کانتینرهای قفل:** نمایش داده می‌شوند ولی کنترل نمی‌شوند. کانتینرهای خود پنل همیشه قفل‌اند.
- **نمایش لاگ در ربات‌ها:** پیش‌فرض خاموش، چون لاگ‌ها ممکن است اطلاعات حساس داشته باشند و به سرورهای پیام‌رسان کپی می‌شوند.
- **هشدارها:** کدام کانتینرها پایش شوند و آستانه‌ی CPU و RAM کانتینر، حلقه‌ی ری‌استارت، RAM سرور و دیسک Docker. عدد `0` آن بررسی را خاموش می‌کند.

@@article containers-bot
@title کنترل کانتینرها از ربات
@summary دیدن و کنترل کانتینرها از بله و تلگرام با کد Google Authenticator.
در منوی ربات **کانتینرها** را بزنید (اگر چند سرور دارید، اول سرور را انتخاب کنید). فهرست با مشکل‌دارها در ابتدا، جزئیات، مصرف، وضعیت سرور و، اگر اجازه داده باشید، ۳۰ خط آخر لاگ نمایش داده می‌شود.

**شروع، توقف و ری‌استارت از ربات به کد Google Authenticator نیاز دارد:**

1. دکمه‌ی کار را بزنید.
2. ربات کد ۶ رقمی فعلی برنامه‌ی Authenticator یک حساب پنل با [ورود دو مرحله‌ای](#two-factor) روشن را می‌خواهد.
3. کد را ظرف ۲ دقیقه بفرستید.

اگر هیچ حسابی ورود دو مرحله‌ای ندارد، از ربات فقط می‌شود کانتینرها را دید. بعد از ۵ کد اشتباه در ۱۵ دقیقه، کنترل از ربات ۱۵ دقیقه مسدود می‌شود. پس حساب پیام‌رسانِ دزدیده‌شده نمی‌تواند سرویس‌های شما را متوقف کند.

@@article projects-overview /projects
@title دیپلوی چطور کار می‌کند؟
@summary معرفی بخش پروژه‌ها و نکته‌ی امنیتی مهم.
برنامه‌های خودتان را از یک مخزن git که فایل `docker compose` دارد، روی سرور دیپلوی کنید؛ از پنل یا ربات. پنل لاگ هر دیپلوی را نگه می‌دارد، با یک کلیک نسخه‌ی قبلی را برمی‌گرداند و می‌تواند درست قبل از هر دیپلوی از دیتابیس‌های برنامه بکاپ بگیرد.

پیش‌نیاز: [agent روشن باشد](#containers-enable) (روی سرور خود پنل) یا سرور مقصد [وصل شده باشد](#add-server). پوشه‌ی پروژه‌ها (پیش‌فرض `/opt/mbp-projects`) باید متعلق به کاربر `10001` باشد.

> ! **هر کس بتواند دیپلوی کند، هر کاری روی آن سرور می‌تواند انجام دهد**، چون یک فایل compose می‌تواند فایل‌های سرور را mount کند یا کانتینر privileged بسازد. فقط مدیران دیپلوی می‌کنند، دیپلوی از ربات کد Google Authenticator می‌خواهد و هر دیپلوی با نام درخواست‌کننده ثبت می‌شود.

@@article add-project /projects/new
@title افزودن پروژه
@summary تعریف مخزن، دسترسی، متغیرها و بکاپ قبل از دیپلوی.
**پروژه‌ها ← پروژه‌ی جدید**:

- **نام:** حروف کوچک انگلیسی، عدد، `-` و `_`. همین نام، نام پروژه‌ی compose روی سرور است و بعد از اولین دیپلوی تغییر نمی‌کند.
- **سرور:** پروژه روی [سرور فعال](#current-server) ساخته و دیپلوی می‌شود (فرم نامش را نشان می‌دهد). بعد از اولین دیپلوی قابل تغییر نیست.
- **مخزن، شاخه، فایل compose:** `https://…` یا `git@host:owner/repo.git`، شاخه‌ی دیپلوی، و مسیر فایل compose داخل مخزن (پیش‌فرض `docker-compose.yml`).
- **دسترسی به مخزن خصوصی:**
  - **کلید SSH (پیشنهادی):** با `ssh-keygen -t ed25519 -N "" -f deploy_key` بسازید، `deploy_key.pub` را در مخزن به‌عنوان deploy key فقط‌خواندنی اضافه کنید (GitHub: Settings ← Deploy keys) و کلید خصوصی را در پنل وارد کنید.
  - **توکن:** توکنی با دسترسی خواندن مخزن (GitHub: Contents: read؛ GitLab/Gitea: `read_repository`).
- **متغیرهای محیطی:** در هر دیپلوی در فایل `.env` کنار فایل compose نوشته می‌شوند. در compose با `env_file: .env` یا `${NAME}` استفاده کنید. مقدارها رمزنگاری‌شده ذخیره و دیگر نمایش داده نمی‌شوند؛ برای نگه داشتن، خالی بگذارید. **بارگذاری فایل .env** یا **چسباندن .env** متغیرها را از یک فایل `.env` موجود پر می‌کند: نام‌هایی که هست مقدار جدید می‌گیرند، نام‌های تازه اضافه می‌شوند و خط‌هایی که متغیر نیستند گزارش می‌شوند. تا «ذخیره» را نزنید چیزی ذخیره نمی‌شود.
- **پوشه:** اختیاری؛ پروژه‌های مرتبط را در صفحه‌ی پروژه‌ها کنار هم نگه می‌دارد (مثلاً سرویس‌های یک محصول). فقط برای پنل است و فایل‌ها روی سرور جابه‌جا نمی‌شوند.
- **بکاپ قبل از دیپلوی:** سرور دیتابیس و دیتابیس‌ها را انتخاب کنید. با گزینه‌ی «اگر بکاپ ناموفق بود، دیپلوی انجام نشود» بدون بکاپ تازه چیزی دیپلوی نمی‌شود.

> کلید و توکن رمزنگاری‌شده ذخیره می‌شوند، هرگز دوباره نمایش داده نمی‌شوند و در لاگ‌ها پوشانده می‌شوند.

@@article deploy /projects
@title دیپلوی و مراحل آن
@summary آنچه بعد از زدن «دیپلوی» اتفاق می‌افتد.
در صفحه‌ی پروژه **«دیپلوی»** را بزنید (یا از ربات). لاگ زنده نمایش داده می‌شود:

1. **بکاپ** دیتابیس‌های انتخاب‌شده (اگر تعیین شده باشد).
2. **دریافت:** آخرین commit شاخه از git. فایل‌هایی که در مخزن نیستند (مثل پوشه‌های داده) دست نمی‌خورند.
3. **ساخت:** `docker compose pull` (اگر pull نشد، ایمیج‌های موجود استفاده می‌شوند) و `docker compose build`.
4. **اجرا:** `docker compose up -d --remove-orphans`.
5. **بررسی:** سرویس‌ها تا یک دقیقه زیر نظر هستند. اگر یکی با خطا خارج شود، مدام ری‌استارت شود یا health check آن شکست بخورد، دیپلوی ناموفق است و علت (مثلاً «worker: exited with code 3») نمایش داده می‌شود.

- هم‌زمان فقط یک دیپلوی برای هر پروژه اجرا می‌شود.
- نتیجه به‌صورت هشدار «دیپلوی موفق / ناموفق» ارسال می‌شود و دیپلوی‌ای که از ربات شروع شده، در همان گفتگو گزارش می‌شود.
- **از ربات:** پروژه‌ها ← پروژه ← دیپلوی، و کد Google Authenticator.
- **حذف پروژه:** پروژه از پنل حذف می‌شود و اگر تیک بزنید، کانتینرهایش متوقف و حذف می‌شوند (`docker compose down`؛ volumeها و داده‌ها می‌مانند). تاریخچه‌ی دیپلوی می‌ماند.

@@article build-elsewhere /projects
@title build روی سرور دیگر
@summary ایمیج‌ها روی یک سرور ساخته و روی سرور دیگر اجرا شوند.

به‌طور پیش‌فرض خود سرور پروژه کد را دریافت می‌کند، ایمیج‌ها را می‌سازد (`docker compose build` که پردازنده، حافظه و دانلود زیادی لازم دارد) و اجرا می‌کند.

در فرم پروژه، **محل build ← build روی** می‌تواند یک سرور متصل دیگر باشد:

1. آن سرور کد را دریافت و build می‌کند؛ چیزی آنجا اجرا نمی‌شود.
2. پنل ایمیج‌ها را فشرده از agent آن سرور به سرور پروژه می‌فرستد.
3. سرور پروژه همان commit را (برای فایل compose و پیکربندی‌ها) دریافت و ایمیج‌ها را بدون build اجرا می‌کند.

لاگ استقرار مرحله‌ی **ارسال ایمیج‌ها** و حجم ارسال‌شده را نشان می‌دهد. وقتی سرور پروژه ضعیف است یا اینترنتش محدود است این گزینه را انتخاب کنید. ارسال ایمیج‌های بزرگ زمان می‌برد و agent هر دو سرور باید به‌روز باشد ([به‌روزرسانی agent](#server-maintenance)).

@summary برگرداندن یک دیپلوی خراب با یک کلیک.

@title نکات سرورهای داخل ایران
@summary دریافت ایمیج‌ها و بسته‌ها وقتی دسترسی به اینترنت محدود است.

@@article two-factor /account
@title ورود دو مرحله‌ای (Google Authenticator)
@summary روشن کردن کد ۶ رقمی برای ورود به پنل.
پس از گذرواژه، یک کد ۶ رقمی از برنامه‌ی احراز هویت روی گوشی هم لازم می‌شود (Google Authenticator، Microsoft Authenticator، Aegis، 2FAS یا هر برنامه‌ی TOTP).

1. به [حساب کاربری](/account) بروید و **«روشن کردن»** را بزنید.
2. گذرواژه را تأیید کنید.
3. QR را با برنامه اسکن کنید (یا کلید را دستی وارد کنید).
4. کد نمایش‌داده‌شده در برنامه را وارد کنید.
5. **۸ کد بازیابی** نمایش داده می‌شود؛ آن‌ها را جای امنی جدا از گوشی نگه دارید. فقط همین یک بار دیده می‌شوند.

- بعد از روشن کردن، نشست‌های دیگر این حساب خارج می‌شوند.
- مرحله‌ی دوم باید ظرف ۵ دقیقه پس از گذرواژه انجام شود.
- هر کد فقط یک بار کار می‌کند. ساعت سرور و گوشی باید درست باشد (اختلاف ±۳۰ ثانیه پذیرفته می‌شود).
- **خاموش کردن** گذرواژه و یک کد فعلی (یا کد بازیابی) می‌خواهد.
- برای کنترل کانتینرها و دیپلوی از ربات، دست‌کم یک حساب باید ورود دو مرحله‌ای داشته باشد.

@@article recovery-codes /account
@title کدهای بازیابی و چند دستگاه
@summary ورود بدون گوشی و اضافه کردن گوشی دوم.

## ورود با کد بازیابی

در مرحله‌ی دوم ورود، **«استفاده از کد بازیابی»** را بزنید. هر کد یک بار کار می‌کند. وقتی کدها کم شدند، **«کدهای بازیابی جدید»** بسازید (کدهای قبلی باطل می‌شوند).

## چند گوشی یا چند حساب گوگل

یک کلید را می‌شود روی چند گوشی یا چند برنامه اضافه کرد؛ همه کد یکسان نشان می‌دهند. یا هنگام راه‌اندازی QR را روی همه اسکن کنید، یا بعداً با **«افزودن دستگاه دیگر»** (گذرواژه و یک کد فعلی) همان کلید را دوباره ببینید؛ کلید عوض نمی‌شود.

## هم گوشی و هم کدها گم شده‌اند

کسی که به سرور دسترسی شل دارد می‌تواند ورود دو مرحله‌ای را خاموش کند:

```bash
docker compose exec backend python -m mbp.cli disable-2fa admin
```

سپس با گذرواژه وارد شوید و دوباره راه‌اندازی کنید.

@@article forgot-password
@title فراموشی گذرواژه یا قفل شدن
@summary بازیابی دسترسی از روی سرور.
روی سرور، در پوشه‌ی پنل:

```bash
# list admins
docker compose exec backend python -m mbp.cli list-admins

# new password (asked twice, at least 10 characters)
docker compose exec backend python -m mbp.cli reset-password admin

# or generate and print a random one
docker compose exec backend python -m mbp.cli reset-password admin --generate
```

- `reset-password` همه‌ی نشست‌های آن مدیر را هم می‌بندد و قفل ناشی از ورودهای ناموفق را برمی‌دارد.
- ورود دو مرحله‌ای را خاموش نمی‌کند؛ برای آن `disable-2fa` را ببینید.
- بعد از ۵ ورود ناموفق در ۱۵ دقیقه، نام کاربری ۱۵ دقیقه قفل می‌شود و قفل خودبه‌خود هم باز می‌شود.

@@article security-notes
@title نکات امنیتی
@summary خلاصه‌ی سازوکارهای امنیتی پنل و توصیه‌ها.

- همه‌ی صفحه‌ها و APIها به ورود نیاز دارند (جز صفحه‌ی ورود و `/api/health`).
- نشست‌ها پس از ۳۰ دقیقه بی‌فعالیتی بسته می‌شوند. پس از ۵ ورود ناموفق، نام کاربری ۱۵ دقیقه قفل می‌شود.
- رمز دیتابیس‌ها، کلید فضای ابری، توکن ربات‌ها، توکن سرورها، کلیدهای مخزن و متغیرهای پروژه‌ها **رمزنگاری‌شده** ذخیره می‌شوند و هیچ‌وقت در پاسخ‌ها یا لاگ‌ها نمی‌آیند.
- `docker.sock` فقط به agent داده می‌شود، نه به خود پنل.
- پنل به‌صورت پیش‌فرض فقط از روی خود سرور در دسترس است ([تونل SSH](#access)).

توصیه‌ها:

- ورود دو مرحله‌ای را روشن کنید.
- از `MBP_ENCRYPTION_KEY` و کدهای بازیابی نسخه‌ی امن نگه دارید.
- کلیدها و توکن‌ها را هرگز در چت یا تیکت نفرستید؛ اگر فرستادید، فوراً باطل و تعویض کنید.
- برای دیتابیس‌ها [کاربر اختصاصی با کمترین دسترسی](#backup-user) بسازید.
- روی باکت فضای ابری Object Lock یا قانون نگهداری فعال کنید.

@@article update
@title به‌روزرسانی پنل
@summary گرفتن آخرین نسخه بدون از دست رفتن اطلاعات.
در پوشه‌ی پنل روی سرور:

```bash
git pull
docker compose up -d --build
docker image prune -f
```

دستور آخر اختیاری است و ایمیج‌های قدیمی را پاک می‌کند.

- مایگریشن‌های دیتابیس خودکار هنگام شروع اجرا می‌شوند و تنظیمات، دیتابیس‌ها، زمان‌بندی‌ها و بکاپ‌ها حفظ می‌شوند.
- قبل از به‌روزرسانی‌های بزرگ، از [خود پنل بکاپ](#panel-backup) بگیرید.
- اگر agent روشن است، با همین دستور به‌روز می‌شود. agent سرورهای دیگر جداگانه روی همان سرورها [به‌روز می‌شود](#server-maintenance).

@@article panel-backup
@title پشتیبان از خود پنل
@summary از چه چیزهایی باید نسخه داشته باشید و چطور.
همه‌ی دانسته‌های پنل در دو جاست:

- **فایل `.env`**، مهم‌تر از همه `MBP_ENCRYPTION_KEY`. بدون آن رمزهای ذخیره‌شده قابل بازگشایی نیستند. یک نسخه جای امن بیرون از سرور نگه دارید.
- **volume `mbp-data`**: دیتابیس خود پنل (وقتی SQLite پیش‌فرض است). با PostgreSQL یا MySQL از همان دیتابیس بکاپ بگیرید.

ذخیره‌ی دیتابیس پنل در یک فایل:

```bash
docker compose stop backend
docker compose run --rm --no-deps -T --entrypoint tar backend czf - -C /data . > mbp-data-$(date +%F).tgz
docker compose start backend
```

فایل‌های بکاپ خودشان در volume `mbp-backups` هستند و اگر فضای ابری روشن باشد، در باکت هم هستند.

@@article move
@title انتقال به سرور دیگر
@summary جابه‌جا کردن کامل پنل.

1. روی سرور قدیم [بکاپ پنل](#panel-backup) بگیرید و `.env` و فایل `.tgz` را به سرور جدید ببرید.
2. روی سرور جدید کد را بگیرید، **همان** `.env` را در پوشه بگذارید (همان `MBP_ENCRYPTION_KEY`) و بازگردانی کنید:

```bash
docker compose up --no-start --build
docker compose run --rm --no-deps -T --entrypoint tar backend xzf - -C /data < mbp-data-2026-10-12.tgz
docker compose up -d
```

3. در صفحه‌ی هر پایگاه داده «آزمایش اتصال» را بزنید. فایل‌های بکاپ محلی منتقل نمی‌شوند؛ در صورت نیاز volume `mbp-backups` را هم به همین روش (`-C /backups`) منتقل کنید یا از فضای ابری دریافت کنید.

| ------------------------------------------- | ---------------------- | ----------------------------------------------------------------------------------------- |
| `MBP_ENCRYPTION_KEY`                        | (الزامی)               | کلید رمزنگاری رمزها؛ برای چرخش کلید چند کلید را با ویرگول جدا کنید (اولی رمزنگاری می‌کند) |

| `MBP_RETENTION_INTERVAL_MINUTES`            | `60`                   | تناوب اجرای سیاست نگهداری                                                                 |

| `MBP_SCHEDULE_MISFIRE_GRACE_SECONDS`        | `300`                  | مهلت اجرای زمان‌بندی‌ای که پنل هنگامش خاموش بوده                                          |
| `MBP_BOTS_ENABLED`                          | `true`                 | کلید اصلی ربات‌ها                                                                         |

@@article uninstall
@title حذف پنل
@summary پاک کردن کامل یا نگه داشتن داده‌ها.

```bash
docker compose --profile containers down
```

با دستور بالا کانتینرها حذف می‌شوند و داده‌ها می‌مانند. برای حذف volumeها هم (دیتابیس پنل و فایل‌های بکاپ محلی):

```bash
docker compose --profile containers down -v
```

> ! با `-v` همه‌ی بکاپ‌های محلی پاک می‌شوند. نسخه‌های فضای ابری دست نمی‌خورند؛ اگر لازم نیستند، از کنسول همان سرویس حذف کنید.

سپس پوشه‌ی پنل را پاک کنید. روی سرورهای دیگر agent را با `docker compose -f docker-compose.agent.yml down -v` حذف کنید.

@@article faq
@title پرسش‌های متداول
@summary جواب کوتاه به سؤال‌های رایج.

## بکاپ گرفته شد ولی در فضای ابری نیست؟

کلید «بارگذاری نسخه‌های پشتیبان در فضای راه دور» را در تنظیمات و گزینه‌ی همان پایگاه داده (همیشه/هرگز/سراسری) را بررسی کنید. وضعیت آپلود و خطای آن در [پشتیبان‌ها](/backups) نمایش داده می‌شود ([راهنما](#remote-storage)).

## چرا نمی‌توانم نسخه‌ی ابری را حذف کنم؟

نسخه‌های ابری تا ۷ روز پس از آپلود محافظت می‌شوند ([توضیح](#remote-protection)).

## دیتابیسم در فهرست نیست.

کاربر دیتابیس به آن دسترسی ندارد؛ [دسترسی‌ها](#backup-user) را بررسی کنید.

## بکاپ با «دسترسی ناکافی» ناموفق شد.

دسترسی‌های `SELECT, SHOW VIEW, TRIGGER, EVENT, LOCK TABLES` را به کاربر بدهید.

## چطور روی سرور دیگری کار کنم؟

روی کارت **سرور فعال** پایین منو بزنید و سرور را انتخاب کنید ([راهنما](#current-server)).

## دیتابیس یا پروژه‌ای که اضافه کرده بودم دیده نمی‌شود.

احتمالاً سرور دیگری فعال است. در کارت سرور فعال، سروری را که آن را روی‌اش اضافه کرده‌اید انتخاب کنید.

## ربات جواب نمی‌دهد.

- در [ربات‌ها](/bots) وضعیت «متصل» باشد.
- شما در «مدیران ربات» ثبت و فعال باشید.
- در گفتگوی خصوصی پیام بدهید، نه گروه.
- برای تلگرام روی سرور ایران، پراکسی لازم است.

## ربات برای ری‌استارت کانتینر کد می‌خواهد ولی کدی ندارم.

باید دست‌کم یک حساب پنل [ورود دو مرحله‌ای](#two-factor) داشته باشد؛ کد همان برنامه را بفرستید.

## می‌شود یک Google Authenticator را روی چند گوشی داشت؟

بله؛ [کدهای بازیابی و چند دستگاه](#recovery-codes) را ببینید.

## صفحه‌ی کانتینرها می‌گوید agent در دسترس نیست.

روی سرور خود پنل [مدیریت کانتینرها را روشن کنید](#containers-enable). برای سرورهای دیگر [رفع اشکال سرورها](#server-troubleshoot) را ببینید.

## سرور را تازه نصب کردم و «گواهی عوض شده» می‌بینم.

اگر خودتان agent را دوباره نصب کرده‌اید (و volume آن پاک شده)، در [سرورها](/servers) «اتصال» را دوباره بزنید.

## زمان‌بندی اجرا نشد.

نتیجه‌ی آخرین اجرا کنار زمان‌بندی را ببینید؛ معمولاً «پایگاه داده‌ای علامت نخورده» است. منطقه‌ی زمانی را هم بررسی کنید.

## پنل را از بیرون سرور باز نمی‌کنم.

طبیعی است؛ پنل فقط روی سرور گوش می‌کند. از [تونل SSH](#access) استفاده کنید.

## رمز ورود را فراموش کرده‌ام.

[فراموشی گذرواژه](#forgot-password) را ببینید.
